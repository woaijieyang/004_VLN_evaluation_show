# 2026-10-29：测评隔离、通用接入与及时更新

本轮用户反馈是不同测评杂糅、状态归属不清，以及采集不及时。仅使用命令行和HTTP检查，没有操作电脑窗口，也没有启动模型调用、导航或GPU测评。

## 根因与修复

1. 总入口原来直接返回全部任务，前端只按run显示名称筛选。现在总入口仅选择，未选测评时任务列表为空；测评页面根据端口绑定的唯一evaluation ID加载任务。
2. 选择器只认识Case1 trace和无source_run的SDK记录，遗漏了适配器写入的其他来源。现在所有有效索引来源都可分类；标准JSONL也可直接发现，不要求Case1布局或特定模型/数据集名称。
3. 同名run、同模型在不同来源目录可能共用Episode身份。新记录将来源目录纳入身份；已有ID与导入游标保持兼容。不根据缺失信息改写既有结果。
4. 同步状态和手动刷新使用全项目数据源，共享“最后选择”也可能覆盖其他页面或重启时的数据源。现在任务、同步、刷新和实时通知均限定当前测评，启动保留显式配置的监听源；另一个页面的选择不覆盖本页。
5. SDK每步同步合成完整大画面，拖慢消费队列。现在先存观测和步骤，导出时按需合成；活跃trace独立每0.5秒检查追加。SSE使用本测评记录修订，不再依赖全库最大更新时间。

使用21个64×64合成观测，首步单独统计冷启动，后20步测量从`record_step`提交到HTTP replay可读到对应实际step的延迟。没有调用模型/模拟器，没有测浏览器绘制。

| 平台 | 冷启动 | 后20步P50 | 后20步P95 | 丢帧 |
|---|---:|---:|---:|---:|
| Windows | 0.219秒 | 0.073秒 | 0.101秒 | 0 |
| Linux | 0.122秒 | 0.022秒 | 0.024秒 | 0 |

这些数字是小型CPU工程样本，不是实际模型负载、满分辨率传感器或浏览器端到端P95证明。

## 仍需明确的限制

- 任何模型遵循SDK或JSONL约定即可接入；未知私有日志格式仍需适配器。只有成绩不能恢复图像/动作/位置。
- 已停更记录不等于模型仍运行，未收到终止事件不伪装成完成。刷新详情显示最近索引时间和停更时长，无法证明源进程状态时保持未知。
- 已丢失的帧或终止消息不能补造。旧常驻采集进程不会热换Python模块；下一次正常启动后加载新版SDK。生产端正常退出时必须调用end_episode和close。
- 没有Mac实机、本轮浏览器点击/另存为或整机断网验收，没有新增真实导航；已完成的CPU/HTTP检查不替代这些项目。
